# End-to-end cases.

Each directory in `cases/` is one slow query that QUAACK should handle in a known way. It includes the schema and data, the query, and what QUAACK should find. `verify.rb` proves each case's claims against a real Postgres, so the expectations aren't guesses.

The cases are the corpus for the end-to-end test in BACKLOG task 20260922-65. That test will run QUAACK on each case and compare its report with the case. `verify.rb` doesn't run QUAACK. It only checks that the cases themselves are right.

## Running it.

```
ruby e2e/verify.rb             # every case, about 25 minutes
ruby e2e/verify.rb 001 046     # only cases whose directory starts with these
ruby e2e/verify.rb --write     # also rewrite each results.md, and CASES.md after a full run
```

It needs Docker and the standard library, nothing else. It starts its own throwaway `postgres:18` container with autovacuum off (as README step 4 requires of the run server), labeled `quaack.e2e`, loads each case into a fresh database that it drops afterwards, and removes the container and its volume at exit. A container left by a crashed run is removed by the next one. Set `QUAACK_E2E_IMAGE` to use another image, such as the HypoPG one from `spec/support/postgres/`. The proofs don't need HypoPG, because they build real indexes.

It isn't part of `rake`, because of that run time.

## A case.

| File | What it holds |
| --- | --- |
| `README.md` | What the case is, why the query is slow, and what QUAACK should do. |
| `case.json` | Title, category, the README features it exercises, the comparison mode, the literal sets, and any `settings`: non-default planner settings the production plan ran with, which step 2 would read from its `SETTINGS`. `verify.rb` applies them to every statement. |
| `schema.sql` | Tables, existing indexes, and deterministic data (no `random()`), then `VACUUM ANALYZE`. It sets `default_statistics_target` to 10000 first, so ANALYZE reads every row instead of a random sample, and plans repeat from one load to the next. |
| `slow.sql` | The query as QUAACK receives it at intake, with its slow literals. |
| `fast.sql` | A rewrite that reaches the case's bound, or, for `trap` and `none` cases, the tempting rewrite QUAACK must reject. |
| `indexes.sql` | New indexes that reach the case's bound, or, for `none` cases, the strongest index candidate we know of, which still doesn't help. |
| `slow_unlimited.sql` | For `limit_subset` cases, the query without its `LIMIT`. |
| `results.md` | Generated by `--write`: total blocks per literal set, the verdict, and the bound for the end-to-end test. |

Each literal set replaces text in the queries, such as `{"4242": "31337"}`. The first set is always the slow literals from the plan. Sets marked `"minimax": false` only prove equivalence. They're values 3e wouldn't pick, such as for a placeholder compared with an expression, where 3e keeps the slow literal, so the 14b check skips them. The other sets stand in for 3e's worst-case and typical picks. Where a case leaves out a 3e pick because the original would run for many minutes, its README says so.

## What the end-to-end test should expect.

Each `results.md` ends with the bound for BACKLOG 20260922-65. For `index`, `rewrite`, and `both` cases, QUAACK's top-ranked fix must touch no more total blocks on the slow literals than the case's own fix, and must pass 14b. QUAACK may find a different index or rewrite, often a better covering index, and that still passes. The named fix proves the bound can be reached, and the case README explains why. `none`, `trap`, and `refused` cases state an outcome instead.

## Categories.

| Category | Meaning | What `verify.rb` checks |
| --- | --- | --- |
| `index` | A new index is the fix. | With the index, the query returns the same results, touches more than 5% fewer total blocks on the slow literals, and no more on any other 14b set. |
| `rewrite` | A rewrite is the fix, using existing indexes. | The rewrite returns the same results on every set, and wins as above. |
| `both` | Only a rewrite plus a new index wins. | Same results with and without the index. Rewrite plus index wins as above, and beats the rewrite alone and the index alone by more than 5% each. |
| `none` | Nothing should be accepted (15a). | `indexes.sql` is required and holds the strongest index candidate known. Any tempting rewrite still returns the same results. Neither the rewrite, nor the index, nor both together, pass 14a and 14b. |
| `trap` | A tempting rewrite is wrong. | Its results differ from the original's on at least one literal set, so the data really does disprove it. |
| `refused` | QUAACK v1 must refuse the query. | Only that the query runs on Postgres. |

Total blocks are README step 13's: shared, local, and temp blocks from `EXPLAIN (ANALYZE, BUFFERS)`. Each query runs once to warm up, then three times. A count that moves by more than 1% between the three fails the case, because every claim rests on counts that repeat. A parallel plan can wobble by a block or two, which changes no claim.

## Comparison modes.

- `ordered`: identical output, row for row. Used when the `ORDER BY` is a total order.
- `multiset`: the same rows in any order. The default.
- `limit_subset`: 9d's rule for `LIMIT` with no `ORDER BY`. Same row count, and every row appears in the unlimited original.
- `tolerance`: like `multiset`, with each number compared to within a relative 1e-9, for float aggregates (9d). Rows must have the same number of fields.

## What the proofs can't show.

- They run one data set per case. QUAACK's fixtures in steps 9 and 10 look for counterexamples the case's data might not contain. The `trap` cases make sure the data does contain one.
- They use real indexes, not HypoPG, so they don't check 5a's cost estimates, only the measured blocks of steps 13 and 14.
- Plans can change between Postgres versions. They were measured on Postgres 18.
- Full-table statistics make plans repeatable, but they're more precise than production's usual `default_statistics_target` of 100, so some plans may differ from what a production-like sample would give.
- Cases 020 and 093 are relative to the load date. Run them away from midnight UTC.
